## Findings
1. **minor — api/config.py:4891 (guard coverage is split across two predicates).** The guard is `_resolve_provider_alias(config_provider) == "custom" or _is_local_server_provider(config_provider)`. With the agent tree on `sys.path`, the agent alias table maps `ollama`/`vllm`/`llamacpp`/`llama.cpp`→`custom`; without it, the local table maps only `local`, and the rest are covered by `_LOCAL_SERVER_PROVIDERS`. Both branches together cover every name, and the tests pass with the agent dir set — so there is no gap today, but the correctness of the guard silently depends on two tables in different trees staying consistent. Suggested fix: optional — add a comment naming that dependency (the comment already lists `ollama`, `local`, which is the visible half), or add a test that runs with the agent table absent from `sys.path` (the guard still passes for `ollama` via `_is_local_server_provider` — I verified this by reading, not by running).
2. **minor — unverified sibling of the same bug class (not in scope of the issue).** Step 4's `provider == config_provider` is a raw string comparison; a session provider `lmstudio` against config `model.provider: lm-studio` (a real alias pair in `hermes_cli/auth.py:1473`) also misses and falls through to rule 9 (`@lmstudio:model`). That round-trip is intact for colon-bearing ids (parse splits on the unknown first token), so it is not the #7955 failure shape, and I could not confirm the picker ever stores the aliased form. Flagging as potential follow-up, not a defect in this commit.
3. **nit — tests/test_issue7955_...py:103 (`test_pre_fix_hint_is_the_corrupted_form`).** This test pins the parser's current (lossy) behaviour for `@custom:qwen3.8:27b`. If the parser is ever hardened to peel unnamed `custom` prefixes, this test fails even though nothing regressed. It is defensible as a pin of the failure mode, but it is the closest thing in the file to a source-shape test; a comment acknowledging it may need updating alongside a parser change would help.
4. **nit — docs/architecture/provider-context-model-encoding.md:103.** Rule 9 ("Everything else — `@provider:model`") is correct for the pre-existing code, but note a session provider of bare `custom` against a named-`custom:<slug>` config provider still mints `@custom:<model>`, which resolves to generic `custom` routing, not the named proxy. That is pre-existing behaviour (present before and after this commit — same final return), out of this issue's scope; worth a line in the doc only if the maintainers want it.
